Нужно переработать визуализацию node-editor в существующем проекте.

ВАЖНО:
Это не статическая инфографика и не auto-layout блок-схема.
Ноды уже являются интерактивными элементами редактора и пользователь сам может свободно перемещать их по canvas.
Не нужно принудительно перестраивать расположение нодов.
Не нужно менять архитектуру программы без необходимости.
Сначала изучи существующую реализацию node editor, canvas, edges, runtime execution и состояние нодов.

ЦЕЛЬ

Сделать визуализацию связей и выполнения программы похожей по ощущению на node editors / Unreal Engine Blueprint:

- draggable nodes;
- явные входные и выходные порты;
- плавные curved connections;
- цветовое различие типов связей;
- анимация активного execution flow;
- анимированная передача runtime-данных между нодами;
- визуально живой граф во время исполнения программы;
- runtime-значения продолжают отображаться внутри самих нодов, как сейчас.

При этом сохранить текущий стиль интерфейса проекта:
тёмный canvas, существующие карточки нодов, типографику, runtime badges и общую цветовую палитру.

--------------------------------------------------
1. НЕ МЕНЯТЬ СУЩЕСТВУЮЩУЮ ЛОГИКУ НОДОВ
--------------------------------------------------

Сейчас runtime-данные уже отображаются внутри нода.

Например:

name = input(...)
runtime:
name: "Name"

points = 0
runtime:
points: 0

points += i
runtime:
points: 6

if ...
runtime:
условие: True

Это оставить.

Runtime badge внутри нода показывает состояние самой операции.

Новая система должна ДОПОЛНИТЕЛЬНО визуализировать:
1. выполнение control flow;
2. передачу данных между нодами;
3. активность связей.

Не переносить runtime-данные из нодов исключительно на линии.

--------------------------------------------------
2. ПОРТЫ НОДОВ
--------------------------------------------------

Добавить визуально выраженные ports/handles.

Принцип примерно как в Blueprint:

INPUT ports:
- преимущественно слева;

OUTPUT ports:
- преимущественно справа.

Для control-flow также допустимы специальные execution ports.

Порт должен выглядеть как маленькая точка / круг / ромб / стрелка рядом с границей нода.

Не использовать просто линию, появляющуюся из случайной точки рамки.

Пример:

        ┌──────────────────────┐
Exec ●→ │ for i in range(...)  │ →● Completed
        │                      │
        │              Loop ●──┼────>
        └──────────────────────┘

Названия вроде:
- Loop
- Completed
- True
- False
- Value
- Result

должны находиться около соответствующего порта, а не посреди линии.

Если существующая модель графа пока не содержит ports как отдельных сущностей — введи минимальную модель портов, не ломая текущую архитектуру.

--------------------------------------------------
3. CONTROL FLOW И DATA FLOW
--------------------------------------------------

Визуально разделить два типа соединений.

A. EXECUTION / CONTROL FLOW

Примеры:
- последовательное выполнение;
- тело цикла;
- выход из цикла;
- True / False;
- вызов функции;
- возврат.

Такие линии должны иметь свой единый нейтральный цвет.

Например:
серо-белый / голубовато-серый.

B. DATA FLOW

Передача значений:
- int;
- float;
- string;
- bool;
- list;
- object;
- function argument;
и т.д.

Data connections должны иметь другой визуальный язык.

Желательно сделать цвет connection зависимым от типа данных.

Примерная система:

int      -> голубой
float    -> светло-синий
string   -> оранжевый
bool     -> фиолетовый
list     -> бирюзовый
object   -> зелёный
unknown  -> серый

Не обязательно использовать именно эти цвета, если в проекте уже есть палитра.
Главное — стабильное различие типов.

--------------------------------------------------
4. ФОРМА CONNECTIONS
--------------------------------------------------

Полностью отказаться от визуализации, где связь выглядит как огромный прямоугольный маршрут:

──────────────┐
              │
              │
      ┌───────┘

Основной вид связи должен быть похож на Blueprint / node editors.

Использовать cubic Bezier curves.

Пример:

source ●────────╮
                ╰────────● target

или плавную S-кривую.

Для связи между портами:

P0 = source port
P3 = target port

Контрольные точки примерно:

dx = abs(target.x - source.x)

controlOffset = clamp(dx * 0.5, 40, 220)

P1 = {
    x: source.x + controlOffset,
    y: source.y
}

P2 = {
    x: target.x - controlOffset,
    y: target.y
}

Если target находится слева от source, подобрать корректную fallback-геометрию, чтобы линия всё равно выглядела естественно.

Не пытаться любой ценой избегать пересечений connections.

Короткое пересечение проводов лучше, чем линия длиной 1000px, обходящая весь граф.

--------------------------------------------------
5. ДИНАМИЧЕСКОЕ ОБНОВЛЕНИЕ CONNECTIONS
--------------------------------------------------

Так как пользователь перемещает ноды вручную:

- connection должен обновляться в realtime во время drag;
- порты должны двигаться вместе с нодом;
- curve пересчитывается каждый frame / через текущую систему обновления graph;
- не должно быть задержек и "догоняющих" линий.

Не пересчитывать layout графа при перемещении.

Только geometry edges.

--------------------------------------------------
6. АНИМАЦИЯ EXECUTION FLOW
--------------------------------------------------

Когда выполняется конкретный переход между нодами, соответствующая connection должна визуально активироваться.

Не просто менять цвет всей линии мгновенно.

Сделать эффект движущегося импульса.

Пример визуально:

──────────────●──────>

где яркая точка / glow движется от source к target.

Варианты реализации:

Вариант A:
SVG path + stroke-dasharray + stroke-dashoffset.

Вариант B:
отдельная glowing particle, движущаяся по SVG path через:
getPointAtLength()

Предпочтительно сделать второй вариант либо гибрид.

Во время execution:

1. базовая линия остаётся видимой;
2. линия слегка подсвечивается;
3. вдоль неё проходит яркий pulse;
4. pulse движется именно от source к target;
5. после завершения connection плавно возвращается в обычное состояние.

Пример durations:

очень быстрый режим:
100-200 ms

обычный:
250-500 ms

учебный step-by-step:
скорость зависит от configured execution delay.

Анимация должна учитывать существующую скорость исполнения программы.

--------------------------------------------------
7. АНИМАЦИЯ ДАННЫХ
--------------------------------------------------

Это одна из главных частей задачи.

Когда значение передаётся от одной ноды к другой, показать "data packet", который физически движется по connection.

Пример:

source
  ●──────────[ 6 ]──────────●
                         target

или:

●───────────●──────────────>

где движущийся объект содержит runtime value.

Для небольших значений можно показывать текст:

6
True
"Name"
3.14
[1,2,3]

Для длинных данных использовать сокращение:

"Очень длин..."
[12 items]
{5 keys}
<MyObject>

Data packet:
- маленькая pill/badge;
- соответствует цвету типа данных;
- имеет subtle glow;
- движется по Bezier path;
- не мешает чтению графа.

Значение внутри нода при этом тоже обновляется.

То есть должно происходить:

SOURCE
runtime value меняется
      ↓
data packet летит по connection
      ↓
TARGET
runtime value обновляется

Не нужно задерживать реальную логику программы ради анимации, если архитектура не позволяет.
Можно визуализировать события поверх уже существующей runtime системы.

--------------------------------------------------
8. PATH FOLLOWING
--------------------------------------------------

Для движения particle/data packet по SVG path использовать длину реального path.

Например:

const length = path.getTotalLength();

const point = path.getPointAtLength(
    progress * length
);

particle.style.transform =
    `translate(${point.x}px, ${point.y}px)`;

Не интерполировать просто x/y между нодами, потому что объект должен следовать именно по кривой.

Если проект построен на React:
избегать setState на каждый animation frame для всего графа.

Использовать:
- requestAnimationFrame;
- refs;
- CSS/SVG animation;
- локальное состояние edge;
- либо существующую animation architecture.

Не заставлять весь canvas re-render 60 раз в секунду.

--------------------------------------------------
9. MULTIPLE ACTIVE DATA PACKETS
--------------------------------------------------

Поддержать ситуацию:

одновременно по одной connection могут проходить несколько runtime events.

Особенно:
- циклы;
- функции;
- несколько аргументов;
- быстрый execution.

Не хранить только:

edge.active = true

Нужна модель примерно:

edgeAnimations = [
    {
        id,
        edgeId,
        type: "execution" | "data",
        value,
        dataType,
        startedAt,
        duration
    }
]

После завершения animation entry удаляется.

--------------------------------------------------
10. ЦИКЛЫ
--------------------------------------------------

Сейчас loop визуализируется большой прямоугольной связью.

Нужно приблизить его к normal node-editor semantics.

Loop node должен иметь как минимум:

input:
Exec

outputs:
Loop Body
Completed

Пример:

                ┌───────────────┐
───────────────>│ for ...       │
                │               │
                │ Loop Body ●───┼──────>
                │ Completed ●───┼──────>
                └───────────────┘

Body edge ведёт к телу цикла.

После выполнения body runtime execution возвращается к loop node.

Но обратная связь должна быть обычной Bezier curve, а не гигантской рамкой вокруг половины canvas.

Если body находится справа:

FOR Loop Body ●────╮
                   ╰────● points += i

points += i ●──────────── curved return ─────● FOR

Выход Completed идёт непосредственно на следующий node.

Убрать подписи:
"цикл"
"выход"
стоящие посреди canvas.

Вместо них названия ports:
Loop Body
Completed.

--------------------------------------------------
11. CONDITIONS
--------------------------------------------------

Condition node:

            ┌──────────────┐
Exec ──────>│ if ...       │
            │              │
            │ True     ●───┼────>
            │ False    ●───┼────>
            └──────────────┘

Не рисовать одну общую ветку с подписью "да" где-то через 500px.

True/False должны быть частью самого node.

Во время исполнения:

если condition = True:
- True connection получает execution pulse;
- False остаётся неактивной.

если False:
- наоборот.

Runtime badge внутри condition node:
условие: True

оставить.

--------------------------------------------------
12. ACTIVE NODE
--------------------------------------------------

Кроме edge animation активный node тоже должен реагировать.

При начале выполнения:

- border немного становится ярче;
- появляется subtle outer glow;
- можно слегка усилить background;
- без сильного масштабирования.

Пример:

normal:
opacity / border обычный

active:
box-shadow / glow

finished:
короткий fade к normal.

Не делать постоянную кислотную подсветку.

--------------------------------------------------
13. PORT HOVER
--------------------------------------------------

При наведении мыши на port:

- port слегка увеличивается;
- подсвечивается;
- связанные connections можно немного усилить.

При hover самого edge:
- сделать edge толще / ярче;
- optionally подсветить source и target ports.

Это полезно для сложных графов.

--------------------------------------------------
14. SELECTED EDGE
--------------------------------------------------

Если редактор уже поддерживает selection, добавить selection для connections.

Selected edge:
- немного толще;
- визуально выделяется;
- остаётся читаемым поверх других проводов.

Не мешать runtime animation.

Приоритет rendering:

background edges
active edges
selected edges
data particles
nodes

либо аналогичный разумный порядок.

--------------------------------------------------
15. Z-ORDER
--------------------------------------------------

Connection wires должны находиться под нодами.

Data packet может находиться поверх wire, но не должен залезать поверх текста внутри node.

Желательная структура:

canvas background
↓
connections
↓
connection animation
↓
nodes
↓
node overlays / tooltips

Если particle приближается к node, можно скрывать его под node через clipping/z-index.

--------------------------------------------------
16. CONNECTION WIDTH
--------------------------------------------------

Базовые connections должны быть заметными, но тонкими.

Ориентир:

normal:
1.5-2px

hover:
2-2.5px

active:
2-3px + glow

Не делать линии похожими на рамки layout.

--------------------------------------------------
17. ARROWS
--------------------------------------------------

Направление передачи должно быть понятно.

Можно использовать один из вариантов:

A.
маленькую arrowhead в target;

B.
animated dots сами показывают направление;

C.
оба варианта, но очень ненавязчиво.

Предпочтение:
маленький target marker + animation.

--------------------------------------------------
18. BACKGROUND GRID
--------------------------------------------------

Если canvas уже имеет background — сохранить.

Если grid отсутствует, можно добавить очень слабую сетку / dots, но только если это гармонирует с существующим дизайном.

Не превращать background в яркую инженерную сетку.

--------------------------------------------------
19. PAN / ZOOM
--------------------------------------------------

Убедиться, что animation корректно работает при:

- zoom;
- pan;
- node dragging.

Particle должен оставаться привязан к connection даже когда viewport трансформируется.

Лучше держать nodes, edges и particles внутри одного transformed coordinate space.

Не вычислять положение particle относительно screen coordinates, если canvas использует world coordinates.

--------------------------------------------------
20. PERFORMANCE
--------------------------------------------------

Редактор должен нормально работать минимум примерно с:

100 nodes
200 edges
несколькими одновременными animations.

Не запускать отдельный тяжёлый React re-render на каждую точку движения каждого packet.

Оптимизировать:

- SVG;
- refs;
- RAF;
- memoization;
- path caching;
- локальные animation components.

Пересчитывать path geometry только если:
- source node moved;
- target node moved;
- port geometry changed;
- graph changed.

Не пересчитывать все edges при каждом runtime event.

--------------------------------------------------
21. НЕ ПЕРЕДЕЛЫВАТЬ КАРТОЧКИ БЕЗ НЕОБХОДИМОСТИ
--------------------------------------------------

Существующий внешний вид нод в целом оставить.

Сейчас node имеет примерно:

ASSIGN                  стр. 2
--------------------------------
points = 0

points: 0

глобальная область

Этот layout подходит.

Можно немного адаптировать padding слева/справа под ports.

Не превращать ноды полностью в Unreal Blueprint.

Нам нужен visual language connections из Blueprint, а не копирование Unreal UI.

--------------------------------------------------
22. RUNTIME EVENT API
--------------------------------------------------

Найди существующий механизм, через который интерпретатор сообщает frontend о выполнении строк.

Желательно привести его к событиям примерно такого уровня:

node:enter

{
    nodeId
}

node:exit

{
    nodeId
}

edge:execute

{
    edgeId,
    sourceNodeId,
    targetNodeId
}

data:transfer

{
    edgeId,
    sourceNodeId,
    targetNodeId,
    value,
    dataType
}

condition:result

{
    nodeId,
    value: true
}

loop:iteration

{
    nodeId,
    iteration,
    value
}

Не обязательно использовать именно эти названия.
Адаптируй под существующую архитектуру.

Главное:
UI не должен пытаться сам вычислять, какая связь сейчас активна.
Эта информация должна приходить из runtime/execution layer.

--------------------------------------------------
23. DATA PACKET APPEARANCE
--------------------------------------------------

Пример CSS-концепции:

.data-packet {
    position: absolute;
    pointer-events: none;
    padding: 3px 7px;
    border-radius: 999px;
    font-size: 10px;
    font-family: monospace;
    white-space: nowrap;
    backdrop-filter: blur(...);
}

Сделать визуально аккуратно в стиле существующего UI.

Для очень быстрых операций можно показывать просто glowing dot без текста.

Например:

если animation duration < 150ms:
dot

если >= 150ms:
value badge

--------------------------------------------------
24. EXECUTION HISTORY
--------------------------------------------------

Не оставлять все когда-либо выполненные connections постоянно яркими.

Можно использовать короткий afterglow:

active
↓
bright
↓
0.3-0.7 sec fade
↓
normal

Так пользователь видит недавно пройденный путь, но graph постепенно очищается.

--------------------------------------------------
25. STEP-BY-STEP MODE
--------------------------------------------------

Если существует выполнение построчно / пошагово:

анимация должна особенно хорошо работать там.

При переходе:

Node A
↓
animated edge
↓
Node B

Не перескакивать визуально сразу на следующий node.

Если система исполнения уже имеет configurable delay, синхронизировать animation duration с ним.

--------------------------------------------------
26. ПРИМЕР ВИЗУАЛИЗАЦИИ
--------------------------------------------------

Для кода:

name = input("Как тебя зовут?")

points = 0

for i in range(...):
    points += i

if points > ...:
    message = "Отлично, " + name

ожидаемая структура примерно:

                    ┌────────────────────┐
                    │ name = input(...)  │
                    └─────────●──────────┘
                              │
                              ▼
                    ┌────────────────────┐
                    │ points = 0         │
                    └─────────●──────────┘
                              │
                              ▼
                 ┌──────────────────────────┐
             ●──>│ for i in ...             │
                 │                          │
                 │ Loop Body          ●─────┼──────╮
                 │ Completed          ●─────┼──╮   │
                 └──────────────────────────┘  │   │
                                              │   ▼
                                              │ ┌──────────────────┐
                                              │ │ points += i      │
                                              │ └────────●─────────┘
                                              │          │
                                              │    curved return
                                              │          │
                                              │          ╰───────>
                                              ▼
                                      ┌──────────────────┐
                                      │ if ...           │
                                      │                  │
                                      │ True       ●─────┼───>
                                      │ False      ●─────┼───>
                                      └──────────────────┘

Но это только пример расположения.

ПОЛЬЗОВАТЕЛЬ МОЖЕТ ПЕРЕМЕСТИТЬ ЛЮБУЮ НОДУ КУДА УГОДНО.

Connections должны адаптироваться автоматически.

--------------------------------------------------
27. ЧТО НЕЛЬЗЯ ДЕЛАТЬ
--------------------------------------------------

Не делай:

- принудительный auto-layout после каждого изменения;
- огромные ортогональные прямоугольные connections;
- линии длиной через весь canvas только ради отсутствия пересечений;
- подписи "да", "нет", "цикл", "выход" посреди canvas;
- runtime values только на connection вместо node;
- полное копирование Unreal Engine UI;
- Canvas API, если существующая система уже построена на SVG и её можно нормально расширить;
- огромный rewrite проекта;
- новую библиотеку graph-editor без крайней необходимости;
- изменение семантики существующего интерпретатора.

--------------------------------------------------
28. ПОСЛЕДОВАТЕЛЬНОСТЬ РАБОТЫ

Работай преимущественно с существующими компонентами.

--------------------------------------------------
30. DEFINITION OF DONE
--------------------------------------------------

Результат считается готовым, если:

1. Пользователь может свободно двигать nodes.

2. Connections двигаются вместе с ними без задержки.

3. Connections являются плавными Bezier curves.

4. Connections начинаются и заканчиваются в визуальных ports.

5. Execution flow визуально анимируется от source к target.

6. Data values могут визуально двигаться по connection.

7. Runtime values одновременно продолжают отображаться внутри node.

8. True/False имеют отдельные ports.

9. Loop Body/Completed имеют отдельные ports.

10. Цикл больше не создаёт гигантскую прямоугольную рамку вокруг graph.

11. Неактивные connections визуально спокойные.

12. Активные connections хорошо заметны.

13. После выполнения glow плавно исчезает.

14. Pan/zoom/drag не ломают animation.

15. Быстрое выполнение циклов не приводит к падению FPS.

16. Existing runtime/interpreter behavior не сломан.

17. Existing node dragging не сломан.

18. Existing node UI в целом сохранён.

После выполнения:
- перечисли изменённые файлы;
- кратко объясни новую архитектуру connections;
- укажи, как runtime event превращается в визуальную animation;
- укажи потенциальные места для дальнейшей оптимизации.
